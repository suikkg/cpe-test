# 设计方案审查：Web 控制台 / 状态页 / 速率监控

> 范围：整仓分段审查，重点在 UI 与「UI 监控执行」。审查对象是工作树当前状态
> （v4.3.1 + 未提交的 1925 行改动，含监控标签页、`--ui-bind/--ui-token`、
> `/api/local`、ping 进矩阵、resume 开关）。
> 基线：`cargo test` 426 passed / 0 failed；`cargo clippy --all-targets -D warnings` 干净；
> `cargo fmt --check` 干净。以下结论均已回到源码逐条核对。

## 一句话结论

**没有过度设计，不需要重构。** 这一版新增的监控链路在生命周期上想得比大多数同类
代码都细（三条回收路径、绝对游标、独立 owner_id、定长时间口令比较），几乎每个
非显然的决定都有一段说明「为什么不是更简单的那种写法」。真正需要动的是
**两处进程/资源生命周期的收尾**和**四处前端有界性与口径一致性**，都是局部改动，
不触碰架构。

分级：**P0 两条**（会咬到人）、**P1 四条**（明确的正确性/体验缺陷）、
**P2 四条**（结构与一致性）、**P3 三条**（小）。

## P0

### P0-1　控制台跑过一轮测试后，非 Windows 上 Ctrl+C 再也杀不掉进程

**证据链**（三处都要同时成立，缺一不构成问题）：

- `src/master/ui.rs:399` — `run_master()` 在开始执行前注册取消处理器：
  `crate::cancel::setup_cancel_handler();`
- `src/cancel.rs:53` — 注册用 `Once`，进程内只发生一次且**永不撤销**；非 Windows 分支是
  `let _ = ctrlc::set_handler(request_cancel);`（`src/cancel.rs:80`）。这个 handler 只
  `CANCELLED.store(true)`，不退出进程，也没有 Windows 那套 `PRESS_COUNT` 二次按键升级。
- `src/master/webui.rs:478` — 控制台的取请求循环是
  `while let Ok(request) = server.recv() { handle(request, console); }`，
  **全程不查 `cancel::is_cancelled()`**，`server.recv()` 也没有超时。

于是：控制台启动 → 用户点「开始测试」→ `api_run` 起工作线程调 `run_master` →
handler 落地。此后 SIGINT 被永久吃掉，`serve()` 继续服务，进程不退。用户只能
另开终端 `kill`。Windows 上因为有 `PRESS_COUNT` 升级，按两次能强退，但
`api_run` 里的 `cancel::reset()`（`src/master/webui.rs:1474`）每轮把计数清零，
所以每次都得按两次。

**谁会受伤**：`cpe_test ui` 是双击运行的默认入口（Windows 包里的 `start_ui.bat`），
也是开发/旁路验证在 macOS 上最常走的路径。跑完一轮之后关不掉终端，是那种
「以为程序卡死了」的一类故障。

**方向**：`serve()` 的循环里给一个可中断的出口——最直接的是在 `Console` 上放一个
`shutdown: Arc<AtomicBool>`，`setup_cancel_handler` 之外再单独给控制台装一个
「第二次 SIGINT 直接退」的语义；或者控制台自己在 `run()` 开头就注册 handler，
并让主循环用 `server.recv_timeout()` 轮询取消标志、收到就 `server.unblock()`。
测试里已经有现成范式：`the_console_token_gate_covers_both_the_page_and_the_api`
（`src/master/webui.rs:2497` 附近）就是用 `server.unblock()` 让循环收场的。

### P0-2　控制台进程一死，辅测机上那路监控要留满 2 小时，期间样本缓冲无上限

**证据链**：

- `src/master/webui.rs:1787` — UI 侧起远端监控时写死 `"lease_secs": 7200u64`。
- `src/nic/monitor.rs:573-590` — `sweep()` 判的是 `now - entry.t0 >= lease`，
  **租约从 `t0` 起算，`/monitor/status` 不续租**。所以 7200 是一个硬上限，不是心跳。
- `src/nic/monitor.rs:283-285` — 采样循环每拍 `samples.push(sample)`，
  `src/nic/monitor.rs:279-281` 每次读失败 `errors.push(error)`。
  **两个 `Vec` 都没有上限。**
- 回收路径只有三条，全部依赖控制台进程还活着：页面显式 stop、采样线程自己
  `monitor_abandoned` 后 POST `/monitor/stop`、`reap_dead_monitors`。
  控制台被 `kill` / 崩溃 / 关终端时，这三条一条都不走。
  owner-scoped 的 `/resources/cleanup` 更不会碰它——**独立 owner_id 正是设计目标**
  （`src/master/webui.rs:1780` 注释），代价就是没人替它兜底。

**量级**：`start_owned` 把间隔夹在 200–5000ms（`src/nic/monitor.rs:376`），
最坏 5 samples/s × 7200s = 36,000 个 `MonitorSample`（约 3–4 MB）；网卡被拔掉时
`errors` 再叠一份同量级的 `String`。单次不致命，但**每次控制台异常退出都会新增一份**，
辅测机是常驻进程，重复几次就是几十 MB 加几条一直在读 `GetIfTable2` 的线程。

**方向**（按性价比排序）：
1. 把 UI 监控的 lease 降到分钟级（例如 180s），并让 `spawn_agent_monitor` 的
   轮询顺带续租——加一个 `/monitor/renew`，或干脆让 `status()` 刷新 `t0` 之外的
   一个 `last_touch` 字段供 `sweep` 使用。这是**唯一能真正封住进程猝死缺口**的改法。
2. 给 `MonEntry.samples` / `errors` 加上限（`errors` 尤其应该只留最近 N 条 + 计数）。
   执行链路的单元时长有界，所以这条在今天不咬人；但 UI 监控是第一个**按设计
   就要长跑**的调用方，无界容器的前提已经不成立了。

## P1

### P1-1　浏览器端日志框无上限累积，且 `textContent +=` 是二次方开销

`src/master/webui.html:647`：

```js
box.textContent += d.lines.join('\n') + '\n';
```

服务端镜像封顶 4000 行（`src/util.rs:554`），**浏览器这边一行都不丢**。
而 `src/util.rs:552` 自己写着「一次 120 单元的运行会打出三万多行」。
三万行 × 约 100 字节 ≈ 3 MB 文本节点，`white-space:pre-wrap` 且在
`height:420px; overflow:auto` 的盒子里——布局成本随行数线性涨；
`+=` 每秒把整个字符串读出来再写回去，整轮累计拷贝量是行数的平方级。
长测试跑到后半程，页面会肉眼可见地卡。

**方向**：和服务端同一个策略——保留最近 N 行（4000 即可，和镜像对齐），
超出就从头截掉。

### P1-2　监控曲线的 X 轴是数组下标，不是时间；`MonitorPoint.t` 全链路计算并传输却从未使用

`src/master/webui.rs:59-66` 定义了 `t`（会话相对秒数，注释还专门解释了
为什么用相对时间而不是墙钟），两条采样线程都在填它。
但 `src/master/webui.html:711`：

```js
const x = (i) => (i / (view.length - 1)) * (w - 52) + 46;
```

全文件搜不到任何 `p.t` / `point.t` 的引用。后果不只是「多传了一个字段」：

- 采样停顿（辅测机掉线 30 秒、本机计数器读失败一串）在图上被画成**连续等距**的线，
  看不出中间断了。而这条曲线的用途恰恰是发现掉速/断流——v4.3.1 刚为
  `rx_dropout` 加了一整套判定，页面上却把时间轴抹平了。
- 辅测机侧还叠了一层丢样：`spawn_agent_monitor` 只能读 `latest_sample`
  （`src/nic/monitor.rs:436` 只回最后一个），轮询晚一拍就永久丢一个点。
- 图上没有任何 X 轴刻度，人无法回答「这个坑发生在第几秒」。

**方向**：`x` 改用 `p.t` 做线性映射，并在底部标三个时间刻度。数据已经在手里了。

### P1-3　三处采样点上限互不一致，读数口径也对不上

| 位置 | 值 | 证据 |
|---|---|---|
| 服务端环形缓冲 | 7200 点 | `src/master/webui.rs:56` |
| 浏览器保留 | 3600 点 | `src/master/webui.html:761` |
| 页面文案告诉用户 | 「只保留最近 7200 个采样点」 | `src/master/webui.html:255` |
| 曲线实际绘制 | 最近 600 点 | `src/master/webui.html:709` |

连带出一个用户会当场发现的矛盾：「RX 均值 / 峰值」取自 ≤3600 点
（`src/master/webui.html:767`），而曲线的 Y 轴按最近 600 点归一
（`src/master/webui.html:710`）。**读数里的峰值可以高于图上最高的那条网格线**，
两个数并排放着却不是同一个窗口。另外「均值」在 1s 采样下跑过一小时后
变成滑动均值，标签上没写。

**方向**：统一成一个数（前端和服务端都用 7200），文案改成
「最近 N 点（约 M 分钟）」，读数标签写清窗口。

### P1-4　辅测机侧采样间隔 > 5000ms 会被静默夹紧

界面允许填到 60000ms（`src/master/webui.html:243` `max="60000"`），
服务端也照收（`src/master/webui.rs:1589` `clamp(200, 60_000)`），
但 agent 的 `start_owned` 夹在 `clamp(200, 5_000)`（`src/nic/monitor.rs:376`）。
选 10s 监控辅测机时：agent 实际按 5s 采，控制台按 10s 轮询、按 `elapsed_ms` 去重，
**一半的样本被丢掉且无人知情**；而同样填 10s 监控本机，行为是对的
（`spawn_local_monitor` 自己 sleep）。同一个输入框在两个「监控端」下语义不同。

**方向**：`monside` 选辅测机时把输入框 max 改成 5000，或在服务端夹紧并把
实际生效值回给页面显示。

## P2

### P2-1　`AgentResourceInventory` 零直接测试覆盖，并发/故障测试全打在手写的测试替身上

`src/resource.rs` 451 行里，生产实现是 `AgentResourceInventory`（约 110 行，
`src/resource.rs:68-150`），它委托给三个真实 manager 并**规定了清理顺序**
（先 client、再 server、monitor 最后收，为的是保住终采样）。
其余约 280 行是 `#[cfg(test)]` 的 `InMemoryResourceInventory` 加它的测试。

`grep -rn "AgentResourceInventory::new" src/` 只有两处，**全在 `src/agent/server.rs`
的生产路径上（262、638），没有一处在测试里**。也就是说
「cleanup 幂等」「不误伤别的 owner」「拒绝迟到的 start」这些性质，
证明的是那个手写模型，不是真正跑的那份代码。清理顺序写错、
`stop_owner` 的 `wait` 传错，测试全绿。

**结论**：这是全仓唯一一处我认为**测试替身的收益已经小于漂移风险**的地方。
不必删掉模型（它对推理确实有用），但至少要有一个用真 manager 的
`AgentResourceInventory` 冒烟测试：起一个 monitor + 一个 server，
`cleanup_owner`，断言两者都停了、别的 owner 没被动。

### P2-2　辅测机状态页还是单线程 HTTP，主控控制台刚为同一个理由加了线程池

`src/master/webui.rs:387` 的 `UI_WORKERS = 4` 写得很清楚：
`/api/local` 要跑 `scan_host()`，Windows 上会拉起 ipconfig/netsh 一到两秒，
单线程会让每秒一次的日志轮询和采样轮询全部排队。

**完全相同的情况在辅测机状态页上还在**：`src/agent/webui.rs:217-224` 是
单线程 `for request in server.incoming_requests()`，而 `api_status` 同样调
`scan_host(&[])`（`src/agent/webui.rs:284`），页面每 1.5s 轮询 `/api/activity`、
每 60s 拉一次 `/api/status`（`src/agent/webui.html:258-259`）。
Windows 上每分钟会有一次 1–2 秒的活动表停顿。

**方向**：把 `UI_WORKERS` 那套原样搬过去（两三行），或者给 `scan_host` 结果
加一个几秒的缓存。前者和已有决定一致，更省事。

### P2-3　`logln` 的环形裁剪用 `Vec::drain`，封顶后每行 O(4000) 移动

`src/util.rs:566-569`：镜像满了以后每写一行 `drain(..1)`，要搬 4000 个 `String`
（约 96 KB memmove）。三万行就是约 3 GB 的无谓拷贝。功能上没错，
CPU 上也不至于拖垮什么，但换成 `VecDeque` 是纯赚——
`MonitorData.points` 已经用的就是 `VecDeque`（`src/master/webui.rs:69`），
同一个仓里两种写法没有理由。

### P2-4　`executor.rs`：现状确认，维持「不拆」

生产代码 6768 行（测试模块从 6768 行起，总 11918），其中
`impl Ctx` 从 `src/master/executor.rs:456` 一直到 5131 —— **单个 impl 块约 4700 行、45 个方法**。
这一版没有让它变差（新功能全部落在 webui 侧，`run_master()` 一个入口没动，
这个「不新开执行路由」的约束守得很好）。
前一轮 review（`.ai/REVIEW_PROMPT-v4.2.6.md`）已经把它列为专题，我这次不重复论证，
只记一条：**它仍然是全仓唯一一个「改动前要先读半小时才敢下手」的文件**，
而本次改动之所以低风险，恰恰是因为绕开了它。

## P3

- **`open_url` / `open_path` 在 Unix 上留僵尸进程**：`src/console.rs:71-77`、`:81-87`
  都是 `Command::spawn()` 之后立刻丢弃 `Child`，Rust 的 `Child::drop` 明确不 wait。
  控制台是长驻进程，用户每点一次「打开报告」（`api_open_report`）就多一个僵尸。
  数量由点击次数决定，每个只占一个 PID 表项，Windows 上不存在这个问题。
  一行 `std::thread::spawn(move || { let _ = child.wait(); })` 或收集起来定期 wait 即可。
- **`使用说明.md` 没跟上**：`git diff --stat` 里 README.md 加了 45 行，
  但 52 KB 的中文主手册**一个字没动**——新的「监控」标签页、`--ui-bind`、
  `--ui-token`、`CPE_UI_TOKEN`/`CPE_AGENT_TOKEN`、控制台上的 resume 勾选框、
  PING 进矩阵，全部只存在于 README 的「未发布」段落里。
  手册第 141 行的「四、网卡速率监控」仍然只讲命令行 `cpe_test monitor`。
- **`?token=` 的残留面**：页面加载后 `history.replaceState` 把它从地址栏抹掉了
  （`src/master/webui.html:285`），`Referrer-Policy: no-referrer` 也挡住了 Referer 外泄，
  这两步都做对了。剩下两处没被覆盖：浏览器的**持久化历史库**里仍有那条带 token 的 URL；
  Windows 上 `open_url` 走 `cmd /C start "" <url>`（`src/console.rs:72`），
  token 会出现在 `cmd.exe` 的命令行里——而 `--ui-token` 支持环境变量的初衷
  正是不让它进 `ps`。属于已知取舍，但值得在 README 里点一句。

## 关于「有没有过度设计」的明确立场

**没有。** 逐条看被怀疑的几处：

| 机制 | 是否过度 | 判据 |
|---|---|---|
| 监控会话三条回收路径（显式 stop / 线程自停 / 表回收） | **不过度** | 关标签页不通知服务端，这是硬约束；少任何一条都会漏。缺的反而是第四条（进程猝死，见 P0-2）。 |
| `MONITOR_MAX_SESSIONS = 8` 软上限 | **不过度** | `--ui-bind` 之后确实存在循环调 start 的面；软上限的边界效应也在注释里交代清楚了。 |
| 绝对游标 + `dropped` 计数 | **不过度** | 和 `/api/progress` 同一套语义，复用而非新发明；`monitor_cursor_survives_the_ring_buffer_dropping_old_points` 钉得很准。 |
| 定长时间口令比较 `secret_eq` | **不过度** | 没有失败限速也没有锁定，一旦绑到网络上就是可测的信道。20 行。 |
| `clock.rs` / `nic/counter.rs` 的依赖注入 | **不过度** | 合计 159 行，换来 sweep/采样状态机可以不睡觉地测。 |
| `parser_properties.rs` 376 行 | **不过度** | 整文件 `#![cfg(test)]`，喂任意字节给所有文本解析器——`urldecode` 的 panic 就是这类输入。 |
| `resource.rs` 的内存模型 | **偏重，见 P2-1** | 唯一一处替身收益 < 漂移风险的地方。 |

反过来说，**本次改动里最值得表扬的一条设计判断**是：监控标签页没有新开一条执行
路由，「开始测试」仍然写一份 config 交给同一个 `run_master()`；PING 也没有变成
第四种 transport，而是老老实实映射回配置模型里的 `kinds`
（`src/master/webui.rs:1128-1131`）。这是这套 UI 能在不动 executor 的前提下加功能的根本原因。

## 建议的修复顺序

| # | 事项 | 改动量 | 回归风险 | 怎么验证 |
|---|---|---|---|---|
| 1 | P0-1 控制台可被 Ctrl+C 关掉 | 小 | 低 | 起 ui，跑一轮，Ctrl+C 应退出；已有 `server.unblock()` 范式可复用 |
| 2 | P0-2 lease 降到分钟级 + 续租；`errors` 加上限 | 中 | 中（碰 `sweep`，有单测护着） | 新增：起 UI monitor → 杀控制台 → 断言 agent 在一个 lease 周期内回收 |
| 3 | P1-1 日志框封顶 | 极小 | 无 | 手动灌 5 万行看内存与滚动 |
| 4 | P1-3 三处上限统一 + 读数标签写清窗口 | 小 | 无 | 目视 |
| 5 | P1-2 X 轴改用 `t` + 加时间刻度 | 小 | 无 | 人为断网 30s，图上应出现空档 |
| 6 | P1-4 间隔上限按监控端区分 | 极小 | 无 | 选辅测机 + 10s，确认实际生效值 |
| 7 | P2-2 状态页上线程池 | 极小 | 低 | Windows 上点重新扫描时活动表不应停 |
| 8 | P2-1 给 `AgentResourceInventory` 补冒烟测试 | 小 | 无 | 新测试本身 |

**最低成本、最高收益的第一刀**：P1-1（日志框封顶，改一行）与 P0-1（Ctrl+C）。
前者是所有长测试都会碰到的体验退化，后者是「程序看起来死机了」。

## 最该补的三个测试

1. **控制台在收到取消信号后能退出** —— 直接钉住 P0-1，且能防它复发。
2. **UI monitor 的远端会话在控制台不再续租后被 agent 回收** —— 钉住 P0-2 的修法，

## P1

### P1-5　`extra` 能覆盖所有受控参数，而 `Bytes/sec` 分支用错了进制

两个前提，都实测确认：

**其一，`extra` 追加在受控参数之后，iperf3 取最后一个 `-f`。**
`src/cmd/iperf.rs:101-121` 里 `-f m`、`-t`、`-i 1`、`-p`、`-B` 全写死在前，
最后一句是 `a.extend(req.extra.iter().cloned())`。实跑：

```
$ iperf3 -c 127.0.0.1 -u -b 100M -t 2 -f m -f M
[  5]  0.00-2.01  sec  24.0 MBytes  11.9 MBytes/sec  ...  receiver
```

后写的 `-f M` 赢了。`extra` 来自 config 的 `universal_params` / `link_profiles`，
全仓**没有任何一处校验它**（grep 不到对 `-f` / `-t` / `-i` 的排除）。

**其二，iperf3 的 Byte 单位是 1024 进制，解析器按 1000 进制算。**
同一条 100 Mbits/sec 的流：

```
-f m →  100 Mbits/sec
-f M →  11.9 MBytes/sec        # 100e6/8/1048576 = 11.92，确认是 1024 进制
```

而 `src/cmd/iperf.rs:200-209`：

```rust
let mut mbps = match unit {
    "K" => num / 1000.0,
    "M" => num,              // ← MBytes 被当成 10^6 字节
    "G" => num * 1000.0,
    ...
};
if kind == "Bytes" { mbps *= 8.0; }
```

`11.9 × 8 = 95.2 Mbps`，真值 100 Mbps，**偏低 4.8%**。
K 档偏 −2.3%，G 档偏 −7.0%。

**影响**：偏差量级恰好落在「看着像测量噪声」的区间，不会触发任何断言。
被污染的是工具自报速率列与 `has_measurement()` / `best_receiver()`；
RX 门限走网卡计数器，所以判定不一定跟着错——两个口径**互相矛盾但都不报警**，
这比单纯算错更难查。

**方向**：两处都要动。Bytes 分支改 1024 进制；`extra` 加一层黑名单，
把 `-f` / `-t` / `-i` / `-p` / `-B` 这些「工具自己要控的」参数挡在配置之外，
或者至少在计划提示里写明「你覆盖了 X」。

### P1-6　`RX_DROPOUT` 在两张消费侧的表里都没登记

v4.3.1 的头牌能力是「每个 5 秒窗口都要达标」，产出 `RX_DROPOUT`
（`src/master/rate_window.rs:285`、`src/master/executor.rs:4859`）。
但消费侧有两张表，它一张都没进：

| 表 | 位置 | `RX_UNSTABLE` | `RX_DROPOUT` |
|---|---|---|---|
| 处置建议 | `src/verdict.rs:207` | 有 | **无**（落进 `_ => return None`） |
| 指标交叉核对 | `src/report.rs:708` | 有 | **无**（落进 `_ => reason.to_string()`） |

于是它取代的那个旧码两处都有，它自己两处都没有：报告里既不给下一步该干什么，
也不核对「展示的 RX 均值/P10 是否真的支持这条判定」——而 `validate_rate_reason`
这个交叉核对本身是个很好的设计，正是用来抓判定与展示指标漂移的。

顺带量化一下覆盖面：产出侧的原因码里约有 25 条拿不到处置建议，
除 `RX_DROPOUT` 外还包括 `NIC_DISAPPEARED`、`NO_VALID_MEASUREMENT`、
`RX_P10_BELOW_TARGET`、`IPERF_SUMMARY_LOST` 以及二十来个 `CTSTRAFFIC_*` 运维码。
`_ => return None` 这个兜底意味着**漏登记永远不会有任何信号**。

**方向**：补 `RX_DROPOUT` 两处。更要紧的是加一条测试——
把原因码常量收进一个数组，断言每一条都能拿到建议（或显式登记为「无需建议」），
让下一次新增码时漏登记直接编译/测试失败。

## P2

### P2-5　http_client 对响应体不设任何上限，而两个服务端都设了

```rust
// src/http_client.rs:849-856
let cl = parse_content_length(&head_text);
if let Some(len) = cl {
    buf.resize(len, 0);          // ← len 是对端说了算的 usize
    reader.read_exact(&mut buf)?;
} else {
    reader.read_to_end(&mut buf)?;   // ← 无 Content-Length 时同样无界
}
```

chunked 分支一样：`vec![0u8; size]`（`:876`），`size` 来自十六进制 chunk 头，
且 `out` 会跨 chunk 累加。`grep -n "MAX\|limit\|take(" src/http_client.rs` **一条都没有**。

对照：`src/agent/server.rs:33` 有 `MAX_BODY = 100MB`，控制台有 `MAX_BODY_BYTES`。
**两个服务端都挡了，客户端一侧一个 cap 都没有。**

**谁会受伤**：主控的辅测机 IP 是人手敲进去的。敲到一台跑着别的服务的机器上时，
现在的表现不是「这不是 agent」，而是 `Vec::resize` 直接申请并写满对端声明的长度——
进程 abort 或被 OOM killer 带走。这条链路上没有任何一层能把它降级成一句可读的错误。

**方向**：加一个 `MAX_RESPONSE`（和 agent 的 100MB 对齐即可），
`Content-Length` 超限直接返回错误，`read_to_end` 换成 `take(MAX).read_to_end`，
chunk 累加也计入同一个预算。

### P2-6　`Verdict::Unstable` 已经没有任何产出点，报告却固定渲染一格 `UNSTABLE: 0`

v4.3.1 的说明写着「`UNSTABLE` 不再产出，掉速统一归 `RATE_FAIL`」——代码确实照做了：
`rate_window.rs` 对 `RX_UNSTABLE` 和 `RX_DROPOUT` 都返回 `Verdict::RateFail`。
但这个 variant 的下游全留着：

- `src/report.rs:1468` 数它 —— 恒为 0；
- `src/report.rs:1488` `judged = pass + rate_fail + unstable` —— 加了个恒零项；
- `src/report.rs:1713` 概览里**固定渲染一格 `UNSTABLE` 统计块**；
- `src/master/executor.rs:1860` 一条永不命中的 match 分支。

不是 bug，但报告上一格永远是 0 的指标会被读成「这轮没有不稳定的」，
而实际上是「这个分类已经不存在了」。要么删干净，要么在概览里注明它已并入 `RATE_FAIL`。

### P2-7　三处一起把可用语言钉死在 zh-CN 与 en-US，失败时毫无提示

- `src/cmd/ipconfig.rs:105-121` `adapter_name()` 只认 `"适配器 "` 和 `" adapter "`。
  德语 `Ethernet-Adapter Ethernet:` 里是 `-Adapter`（没有前导空格）、
  日语是 `アダプター`、法语是 `Carte` —— **三者都返回 `None`**。
- `src/nic/scan_windows.rs:141-150` `scan_all()` 的主循环是 `for a in adapters`，
  `adapters` 就是 ipconfig 的解析结果；`GetIfTable2` 的 `if_rows()` 只用来补速率/类型/ifindex。
  所以 ipconfig 解析不出东西 = **一块网卡都扫不到**。
- `src/util.rs:19-23` `decode_bytes()` 是「UTF-8 失败就按 GBK」，
  日语 Windows 的 CP932 会被 GBK 解成乱码。

三条叠起来：非中/英文 Windows 上工具直接不可用，屏幕上只有一句「没有扫到网卡」。
`GetIfTable2` 本身是语言无关的，已经能给出 alias / description / ifindex / speed，
**主循环挂在它上面、ipconfig 只负责补 IP**，就能把这条依赖降到「只有 IP 拿不到」。

（这一条我按代码路径推定，没有非中英文 Windows 可实测，标注为需实机确认。）

### P2-8　`find_iperf3()` 的 `OnceLock` 让常驻进程永远记住「没找到」

`src/cmd/tools.rs:40-68`：查找结果进 `static IPERF3: OnceLock`，
`iperf3_version()` 也走同一个缓存。而 agent 和控制台都是常驻进程。

于是这条完全正常的排障流程走不通：辅测机状态页显示「iperf3 未找到」（橙色告警）
→ 用户把 `iperf3.exe` 拷到程序同目录 → **页面每 60 秒刷新一次，永远还是「未找到」**。
只能重启 agent，而页面上没有任何地方提示需要重启。

这条是首轮那批状态页改动带出来的：以前没有页面时，「未找到」只在启动时打印一次，
缓存一辈子没问题；现在它变成了一个会反复刷新、看起来实时的告警。

**方向**：把 `OnceLock` 换成带 TTL 的缓存（几十秒即可），或者让状态页那条路径走非缓存查找。

### P2-9　`http_client.rs` 1167 行里约 580 行是没有 `#[cfg(test)]` 的故障注入脚手架

`ScriptedExchange` / `ScriptedGate` / `ScriptedEvent` / `ScriptedTransport`
占 `:112` 到 `:694`，全部 `pub`，**没有一处 `#[cfg(test)]`**——
文件里 12 处 `#[allow(dead_code)]` 就是为了盖住它们在非测试构建下的未使用告警。

它们的唯一使用者是 `src/master/executor.rs:6991` 起的测试模块，而那是同一个 crate
的 `#[cfg(test)]` 代码——加 `#[cfg(test)]` 门完全可行，跨模块可见性不受影响。

真实的客户端逻辑（`tcp_request` + `read_http_response` + 两个解析器）只有约 130 行。
**脚手架是它的 4.5 倍**，而且排在文件前半部分，读这个文件的人要先翻过 580 行
测试替身才能看到真正发出 HTTP 的那段。首轮把 `resource.rs` 的内存模型列为
「唯一一处替身收益小于漂移风险」，这一条不同——脚手架本身有价值（`drop_response` /
`truncated` 这些故障是真的难用别的方式造），问题只是**没有关在 `cfg(test)` 里**。

- **`,` 在同一个文件里有两种含义。**`src/cmd/ctstraffic.rs:293`
  `parse_status_number` 做 `replace(',', ".")`（逗号=小数点），

  两者不可能同时对。实际输出里 ctsTraffic 用 `x^N` 表示大数、不打千分位，
  所以今天不咬人；但这是一条留给未来的绊线。
- **`tcp_request` 只用 `addrs.first()`**（`src/http_client.rs:800`），
  解析出多个地址时不回退。`--agent-host` 收主机名时，
  AAAA 先返回而 IPv6 不通就直接失败，不会去试 A 记录。
- **读超时是每次读的超时，不是整个请求的时限**（`src/http_client.rs:806`）。
  对端每隔「略小于 timeout」吐一个字节就能把一次请求无限拖住；
  无 `Content-Length` 的 `read_to_end` 分支尤其。对端是自家 agent 时不成立，
  但它和 P2-5 是同一处缺失的两面。

## 这四块里做对了的地方

不全是问题，有三处值得明确记下来，免得后续重构时被当成可以简化的部分删掉：

1. **`report.rs` 的转义纪律是齐的。** 67 处 `esc()`，且分工清楚——
   `report_endpoint()` 这类拼装函数**不**转义，转义只发生在 `diagnostic_item()`
   这一层，所以不会双重转义。最容易出事的路径（`:1791` 把 iperf3/ctsTraffic
   原始输出内嵌进 `<pre>`）也走了 `esc`。
2. **iperf UDP 丢包解析的三条理由**（`src/cmd/iperf.rs:166-180`）写得很扎实：
   只认 `receiver` 汇总行、直接用 `lost/total` 计数算、取不到就返回 `None` 而不是 0。
   「不知道」和「没丢」分开，这是判定链上最容易偷懒也最容易出事的一处。
3. **`verdict.rs` 把判定收敛到一处**是对的，而且文件开头把「为什么」写清楚了——
   executor 和 report 各写一份优先级顺序曾经产生过两个真实缺陷。
   P1-6 说的是这张表**漏登记了新码**，不是这个收敛做错了。
