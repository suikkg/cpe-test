## C. 低severity 观察
- rate_window.rs:709 `stalled_ratio = longest_zero_delta_run_ms / covered_ms`：
  分子 longest_zero_delta_run_ms 累加的是样本**完整** interval_ms（未按窗口裁剪），
  分母 covered_ms 是裁剪+去重叠后的覆盖时长。窗口两端各一条跨界样本会让分子
  略微偏大。已有 .clamp(0,1) 兜底，且 180s 窗口下两个采样周期远达不到 5% 门槛，
  实际不可触发；属口径不一致，非缺陷。
- rate_window.rs:216 scan_excursion：遇到 interval_ms==0 或 rate 非有限的样本会
  **跳过而不中断当前越界段**，理论上会把两段越界连成一段、虚报连续时长。
  interval_ms==0 无时长跳过是对的；rate 非有限在现有构造路径下不可达
  （速率由 delta/interval 算得，interval==0 已先被滤掉）。属防御性备注。
- resource.rs:108 `let _before_cleanup = self.list_owner(owner_id);` 结果立即丢弃。
  注释说是为了让「生产与模型的清理可观测性一致」，但没有任何消费者。
  代价是三个 manager 各取一次锁 + 一次排序的无用功。属可删的死代码。

## D. 本次 review 找到的最有价值的一条（agent 认证前的内存放大）
**src/agent/server.rs:297-306** —— 请求体在**认证之前**被完整读进内存。
- 33 行 `MAX_BODY = 100 * 1024 * 1024`（100 MiB），32 行 `WORKERS = 16`。
- 297-302 先 `read_to_end` 到 Vec，再 `String::from_utf8_lossy(&bytes).into_owned()`
  又拷一份（合法 UTF-8 时 from_utf8_lossy 返回 Borrowed，into_owned 必然复制）。
- 306 行才做 token 校验。
- 结论：未认证的同网段主机可让 agent 峰值分配 16 × 100 MiB × 2 ≈ 3.2 GiB。
  agent 默认 `agent_bind = 0.0.0.0`，且 config.rs 默认 agent_token 为空。
- agent 的合法请求体都是 KB 级的 JSON 控制消息（大数据在**响应**侧，不在请求侧），
  100 MiB 没有任何用途上的理由。
- 修法（二选一，建议都做）：
  1. 把认证提到读 body 之前（request_authorized 只看 header，不需要 body）；
  2. MAX_BODY 降到 KB 级（如 1 MiB，与控制台 webui.rs:30 的 MAX_BODY_BYTES 对齐），
     并用 String::from_utf8(bytes) 避免第二次拷贝。
- 对照：master/webui/http.rs:254-257 同样是「先读后认证」，但上限是 1 MiB
  且控制台默认只听回环，风险小得多。
