# ADB 内环测速验证

## 范围

实现包含独立左侧内环页面、专用项目导入导出（schema v2，v1 自动升级）、多电脑 agent 调度与命令行 `cpe_test inner --config inner.example.json [--probe]`，支持明确指定的 RNDIS / Wi-Fi / ETH 所选电脑接口与板侧 LAN IPv4。辅测机可选，本机可独立成轮；按 网口 → 协议 → 方向 → 轮次 逐单元执行，方向含上行、下行与双向并发（一个单元两条腿、两个端口、按共同有效重叠窗口计算）。板侧统计接口与 LAN 地址解耦，接收速率来源分 `nic_strict` / `nic_preferred` / `tool` 三档，网卡口径与工具口径的门限互相独立。独立门限、自包含 HTML、含样本的 JSON 报告与 `inner_runs` 历史。不复用子网配置、运行状态、RESUME 或报告重放；未自动推送板侧工具、修改路由或 root 权限。

## 内环方案 v2 落地实测（2026-09-09）

按 `DESIGN-inner-v2.md` 重做模型、计划、执行、测量与页面之后，在公司内网的自研 CPE + 真机 ADB 上做了三次短测。**这是开发短测，不是产品验收**：门限是为了触发分支临时填的。

### 1. 板侧接口清单（`--probe`）

`/sys/class/net` 一次扫描出 46 个接口。`br0` 持有 `192.168.8.1/24`，成员为 `eth0`、`eth1`、`ra0`、`rai0`、`veth1`；`ccmni2` 持有 `10.200.202.233/29`（蜂窝 WAN，不是被测 LAN）。全部接口 `/proc/net/dev` 与 sysfs 两条路径都可读——**这只说明读得出，不说明每个口的计数都适配被测路径**，见第 3 次短测。同一次探测里 `agent1` 因 HTTP 401 标为 `failed`，但它没有被任何勾选的网口引用，探测照常完成、不阻断。

### 2. 双向并发（TCP，8 秒，单流，`nic_preferred`）

一个 `bidir` 单元，两条腿分别占板侧 56190 / 56191：

| 腿 | 接收端 | 端口 | 来源 | 速率 Mbps | 工具接收 | 采样覆盖 | 有效时长 |
|---|---|---:|---|---:|---:|---:|---:|
| 上行 | 板侧 br0（`/proc/net/dev`） | 56190 | 网卡字节计数 | 855.80 | 868.00 | 99.96% | 8.00s |
| 下行 | master en0 | 56191 | 网卡字节计数 | 875.09 | 872.00 | 99.96% | 8.00s |

两条腿的**共同有效重叠窗口 8.00s**，速率都只取这一段——这是「真的同时在跑」的可证明证据，两次顺序单向给不出这个数。合计 1730.89 Mbps（千兆全双工两个方向各自接近线速），未设合计门限故整单元 MEASURED。同一份配置里另有一条 `enabled: false` 的网口，计划预览把它列在「未参与本轮」，执行时既不预检也不起流。

### 3. 工具兜底与严格模式的分界（TCP 上行，8 秒）

把统计接口故意指到 `rndis0`——接口存在、计数可读，但被测流量不走它，于是判定窗口内计数器 100% 零增长。同一场景跑两种策略：

| 策略 | 网卡口径（独立留存） | 采用来源 | 速率 | 门限 | 判定 |
|---|---|---|---:|---:|---|
| `nic_preferred` | NOT_EVALUATED / COUNTER_STALLED，RX 0.00 | 工具接收汇总 | 906.00 | 工具口径 500 | PASS |
| `nic_strict` | NOT_EVALUATED / COUNTER_STALLED，RX 0.00 | 无可信来源 | 未获取 | — | NOT_EVALUATED |

两点是这次改动的核心，都得到了实测确认：

- **网卡口径不被兜底改写**。兜底腿的 `nic_verdict` / `nic_reason` / `nic_rx_mbps` 仍是 NOT_EVALUATED / COUNTER_STALLED / 0.00，没有被填进任何造出来的样本或覆盖率。
- **严格模式不会被工具数字救活**。同一条链路工具侧明明收到 936 Mbps，`nic_strict` 依然是 NOT_EVALUATED。反过来，`nic_preferred` 的 PASS 比的是**工具口径的 500**，不是网卡门限。

兜底腿同时留下两条诊断：`MEASUREMENT_SOURCE_FALLBACK`（改用了哪个来源、原来源为什么不可信）与 `COUNTER_SOURCE_SUSPECT`（计数器整窗冻结 + 工具侧有可信非零流量 = 该接口计数器不适配本路径的证据）。后者只作诊断，不改判。

### 仍未取得的真机证据

双向并发在非全双工链路（Wi-Fi）上的表现、工具兜底在真正的计数器不适配机型上的结论、32 条网口规模的端到端时间，以及执行中 ADB 拔出 / 断线重连的资源归属，都还没有真机数据。下面 2026-09-08 的 ETH 短测是 v1 时期的证据，不能代替以上任何一条。

## 灌包能力补齐（2026-09-09）

第一版一轮只能测 TCP 或 UDP 中的一种，控制台也只回网卡 RX 与判定，iperf3 自报的收发速率、UDP 丢包和板侧 server 原文都只存在于 HTML 报告或根本没有采集。本次改动：

- `protocols` / `directions` 改为数组，执行矩阵变成 链路 × 协议 × 方向；`unit_count()` 是进度、WebUI `total` 和前端预估时长的唯一口径。重复选择判配置错误，不做去重后继续。
- 并发流数按协议可分别覆盖（`tcp_streams` / `udp_streams`），新增 TCP `-w`、UDP `-l`；两者走 `size_token` 白名单（数字加可选 k/m/g）才拼进命令行，与 `RESERVED_CLIENT_FLAGS` 的约束同向。协议专属档位配在不测该协议的一轮里直接判错，避免填了不生效却无提示。
- 采集并展示 iperf3 自报的发送 / 接收速率与 UDP `lost/total`：`/api/inner/status` 的行、控制台表格、HTML 报告三处同步。丢包只取 `receiver` 汇总行的计数自算，拿不到时报“未知”，不落成 0%。`max_udp_loss_pct` 超限只追加 `UDP_LOSS_HIGH` 诊断，不推翻 RX 判定——与子网 `verdict_assembly` 同一口径。
- 报告详情补齐接收端 RX 分布（P10 / 中位 / P95 / 最小 / 最大、滚动窗口覆盖、计数器零增长占比）、有效时长与配置时长，并首次把板侧 server 原文写进报告（首尾各留 40 行，中间注明省略行数，避免长跑 × 多单元把 HTML 顶爆）。
- 回归：`cargo test` 709 项通过、0 失败；`cargo fmt --check`、本机与 x86_64-pc-windows-msvc 两个目标的严格 Clippy 无告警；前端 `npm run test` 282 项通过、`vue-tsc` 通过、`npm run verify` 通过。

实机复测（2026-09-09，公司内网自研 CPE + 真机 ADB，控制台 `cpe_test ui`）：一份配置勾选 TCP + UDP、上行 + 下行，单链路 ETH，每单元 6 秒、单流、UDP 每流 200 Mbps、丢包门槛 1%。**一轮跑完 4 个单元**（改动前需要分两轮）：

| 协议 / 方向 | 接收接口 | 网卡 RX Mbps | 工具发送 | 工具接收 | UDP 丢包 | 有效时长 | 判定 |
|---|---|---:|---:|---:|---|---:|---|
| TCP 上行 | br0 | 888.70 | 916.00 | 914.00 | — | 6.01/6s | MEASURED |
| TCP 下行 | en0 | 917.09 | 922.00 | 916.00 | — | 6.00/6s | MEASURED |
| UDP 上行 | br0 | 197.90 | 200.00 | 200.00 | 0.000% (0/103603) | 6.00/6s | MEASURED |
| UDP 下行 | en0 | 196.94 | 200.00 | 200.00 | 0.000% (0/103754) | 6.01/6s | MEASURED |

控制台表格、`/api/inner/status` 与 HTML 报告三处数字一致；采样覆盖率均 100%。报告 23 KB，含板侧 server 原文与 RX 分布。结束后板侧 `ps -w` 无 iperf3、无 `/tmp/cpe-inner-*` 残留。门限留空故全部 MEASURED，这是开发短测，不代表产品验收标准；`max_udp_loss_pct` 的超限分支本轮丢包为 0，未被真机触发（有单测覆盖）。

## 验证边界与待现场复核项

速率判定复用 `master::rate_window::evaluate_rx_acceptance`，上行采板侧 RX，下行采 PC RX；工具错误、有效时长、背景业务和采样来源只作诊断。每方向前有背景采样；板侧 server 按本次 PID 回收，停止未确认则不继续。

真实多电脑 agent、RNDIS（本机未发现活动接口）、Windows 真机、公司其他产品、长稳与硬件卸载差异仍须现场复核。Wi-Fi 已完成本机短测，未做其他频段和负载档位的覆盖。尤其多接口同网段时，源 IP 绑定不能替代物理出接口核实；桥计数器可能包含其他业务。USB ADB 采样可能与 RNDIS 共享带宽。
