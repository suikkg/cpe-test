## 结论摘要

- **准确性**：网卡口径的速率统计在全部用例上由独立脚本逐样本复算（累计约 7.9 万项）、按原始计数重算 RX（累计 1000 余条腿）、与两端 OS 网卡计数夹逼，最大误差 < 0.07%；有线封装比与理论值一致；两机时间轴对齐误差中位 −5 ms。
- **判定**：PASS / RATE_FAIL / MEASURED / NOT_EVALUATED / SETUP_ERROR 各分支在真实故障（断流、断网卡、杀进程、控制面中断、端口被挡）下都与 ADR-17 / ADR-18 契约一致；没有出现错误 PASS。
- **稳定性**：30 次控制台起停 + 100 次单机起停、跳过、强杀 agent / 主控 / 工具、Ctrl+C，均在秒级回到空闲、零残留进程与端口；四段浸泡共约 8 h 有效运行，长期驻留的控制台与 agent 资源不增长。
- **修复**：P1 两项（Windows 主控被杀后工具成孤儿占端口；带 Wi-Fi 端点的控制台运行约一半被计划闸门误拒），P2 三项（计划页拓扑不刷新；命令行 CTS 窗口被块缓冲截短；网关诊断一律被跳过），其余为报告透明度、混合 OS、文档与测试稳定性。每项都有证伪过的回归测试。
- **遗留**：A1-F06、B0-03 受环境所限阻断；A1-C08（注入丢包 / 时延）需要 Mac root，未做；观察项 O-01–O-08 记录不改。

观察项（不改代码）：
- O-01 Wi-Fi 网卡计数口径随驱动不同（Windows WLAN 收包按 IP 层计，Win WLAN 发 / Mac en1 收约 1516 B/包），同一应用吞吐在不同 Wi-Fi 驱动上读数可差 ±5%。
- O-02 有线路径每 ~100 包出现一次 30–38 ms 的 RTT 尖峰（随机包序号，非首包）；默认「有线 small 最大 RTT ≤30 ms」在 180 包时会高频判 RATE_FAIL——判定如实，属门限敏感度。
- O-03 macOS 上 Windows 预设的 UDP `-w 256m` 报 `socket buffer size not set correctly`，被归为 RATE_FAIL 而不是 SETUP_ERROR；与 D-02 同类，仅 Mac/Linux 出现，按 2026-08-30 的决定不处理。
- O-04 板侧 `br0`（/proc/net/dev）对有线入口 TCP 的读数只比工具接收速率高约 1%（Wi-Fi 入口 4.5%）：GRO 合并后每段头部只计一次，板侧 TCP 口径比线上字节低约 3–4%。
- O-05 出厂 CTS UDP 帧率 100 在 500 Mbps 时每帧 625 KB，ctsTraffic 自报 99% 错误帧；网卡 RX 数据确实到了，只是按帧校验几乎没有完整帧。只进诊断。
- O-06 ctsTraffic server 由主控强停，它块缓冲的 stdout 尾部（最后数秒状态行与 server 摘要）随进程丢失；判定与窗口取 client 状态行，不受影响。
- O-07 控制面断开时实时进度的网卡读数在本单元内不再轮询（免得每秒撞一次 5 s 连接超时），恢复后剩余时间显示「-」；最终判定用 agent 端完整样本。
- O-08 命令行配置没有链路集合名时，按链路熔断与报表分组共用「发送口 ↔ 接收口」这把键，同一对网口的两个方向各算一条链路；刻意只有一份定义，记录不改。
- iperf PASS 行 `reason_code` 为空、ping PASS 为 `PING_OK`，惯例不统一；整窗都低于 80% 门限时诊断仍写「掉坑」。
- 环境：Windows 防火墙挡住已建立的 TCP 流 10 s 以上后，解除规则数据流也不再恢复（控制连接能恢复）——这是 Windows 网络栈的行为，C07W 的断流因此是 31 s 而不是计划的 10 s。

### 补充测试（FIX5，短时长）

应要求把单元时长压到 10 s（出厂预设 20 s），补跑此前只在旧版本上做过的项目：双机三组矩阵（121 单元）、单机矩阵与命令行 CTS、出厂预设与出厂 CTS、真实控制台流程、Mac 主控 + Windows 辅测、ADB 内环（48 单元）、组合场景中途刷新（页面认出在跑的场景、锁住操作、不重发启动，磁盘上只有 1 份场景）、Playwright 回归 20/20、单机 OS 计数夹逼约 1350 项。灌包单元除下面两个口径问题外全部 MEASURED / PASS，0 SETUP_ERROR；统计审计、RX 重算（误差 ≤0.114%）、夹逼、出口一致全部通过。第 19 轮那次 CTS UDP 失败连跑 10 轮未复现。

两个口径问题经用户确认后在 FIX6 修改并实机复测（见下）：
- **Q-02**：整窗真断流（旁证确认零是真实值）时平均值 ≈0，仍判 NOT_EVALUATED / NIC_RATE_MISSING「没有可用的接收端 RX 速率」，与同行诊断矛盾；verify 下一条从头到尾不通的方向拿不到 RATE_FAIL。实例：出厂预设双向 v6 UDP `-l 14k` 的以太网 → WLAN 腿。
- **Q-03**：停滞门槛是窗口的 5%，10 s 窗口时一个 1 s 零样本即超限 → COUNTER_STALLED（Wi-Fi 双向 v6 TCP 出现一次）。短时长单元对 Wi-Fi 计数器的批量更新更敏感。

### FIX6：Q-02 / Q-03（用户确认口径）

- **Q-02** 旁证确认真断流时，平均值低于有效下限也照常进验收（有门限 RATE_FAIL、无门限 MEASURED），不再判 NIC_RATE_MISSING。
- **Q-03** 停滞门槛 = 超过窗口 5% **且**长于 1.5 个采样间隔；≥20 s 窗口行为不变。

两条新测试（旧逻辑下各自红）；Mac 门禁 959+1、Windows 原生门禁 943+1 全绿。实机：出厂预设双向 v6 UDP `-l 14k` 3 轮 6 单元全部 MEASURED（以太网 → WLAN 腿有 15–25% 真实断流，按平均值照常出数）；Wi-Fi 双向 v6 TCP 10 s 5 轮 0 COUNTER_STALLED；双机冒烟 11 单元、单机 CTS 12 单元全部有结论；审计全部通过。之后再次清理两台机器。
