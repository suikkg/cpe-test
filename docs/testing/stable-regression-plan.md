## 1. 执行约定与角色

开发侧负责变更影响分析、单元/属性/结构测试、协议契约、故障注入及修复；测试侧负责从用户入口构造端到端场景、独立结果对账、真实 Windows 拓扑、性能和交付验收。Claude 可以承担两侧工作，但验收预期不能直接复制待测实现，也不能用更新快照掩盖回归。

用例主表：`stable-regression-cases.csv`（UTF-8 BOM，便于 Excel 打开）。一行是测试点，不代表其中所有参数已经展开。执行前将多参数行拆成子用例，例如 `FLOW-01-W11-UDP-V6-BA`，保留父 ID；补齐前置、精确配置、步骤、清理、数值预期和证据目录。下文矩阵中的组合不能只执行一个代表项后把父项标 PASS。

优先级：P0 为合入阻断；P1 为必须执行的完整回归，若客观不适用须有理由和范围说明。状态使用 `NOT_RUN / RUNNING / PASS / FAIL / BLOCKED / NA`。NA 表示产品不支持或确实不适用；缺设备/时间/权限是 BLOCKED，不能填 NA。父项仅在所有必需子项通过后 PASS。

测试 FAIL 与产品 RATE_FAIL 是两回事：注入低 RX 后正确输出 RATE_FAIL，该测试应 PASS。正常健康链路若大量 NOT_EVALUATED/SETUP_ERROR，必须解释环境或程序原因，不能声称正常吞吐已验收。

## 3. 数值预期与最高风险契约

以下是当前源码核对后的基准；执行前仍需核对候选版本。源码与用户确认产品契约冲突时登记缺陷，不把当前输出自动变成预期。

- `evaluate_rx_acceptance` 先检查 RX 是否可信。覆盖率至少 0.95；可用平均值须有限且严格大于 `MIN_VALID_RX_MBPS`（当前 0.01）；停滞比例大于 `1 - MIN_RATE_SAMPLE_COVERAGE` 会 NOT_EVALUATED。测试浮点邻界时用代码常量表达式及其上下邻值，不靠十进制字符串恰好表示。
- 可信 RX 与有效目标比较：小于 RATE_FAIL，等于/大于 PASS。Observe/Discover 清目标后 MEASURED；Auto 无目标 MEASURED；**Verify 缺目标是 NOT_EVALUATED/TARGET_MISSING**。不能照旧文档简化成“无门限一律 MEASURED”。
- 工具已形成有效流量和可信 RX 的前提下，TX、丢包、丢帧、P10、起流数和运行时错误只走诊断，不改最终速率结论。未起流、setup 失败、单流 UDP 安全尝试耗尽有独立前提层契约，必须分别测。
- 长时间断流可能同时触发计数器不可信。区分“可信均值达标且带瞬降诊断”和“均值已不可信”，不要拿长断流样本强行要求 PASS。
- Wi-Fi 双向合计为 AB 接收端 RX + BA 接收端 RX，不是 TX+RX；配合计门限时腿只测量，单元比较一次。少一腿或一腿不可信时不猜合计。
- 聚合优先级：空集 SETUP_ERROR；任一 SETUP_ERROR；单流硬失败；会遮蔽其他腿的不可信 NOT_EVALUATED；RATE_FAIL；腿内局部 NOT_EVALUATED；MEASURED；含 SKIP；最后才是全 PASS。必须以 `(verdict, reason_code)` 组合测，不能只按标签排序。
- `resume_age_is_fresh` 当前是 **-60 秒 ≤ age < 24 小时**。架构旧章节的“不到 25 小时”已经过时。RESUME ID 与计划 hash 是不同契约；只影响展示的 Wi-Fi 速率抖动不挡跑，实际命令/目标变动仍挡跑。
- 独立复算 RX：用保存的原始计数器和单调时间，按真实窗口裁剪、按有效时长加权、按当前背景扣除规则计算 Mbps；原始精度作判定，显示舍入单独核对。记录原始序列→有效窗口→覆盖率→平均值→目标来源→最终原因码全链路。

## 4. 必跑命令与执行顺序

先检查已提交产物，再重建前端，避免重建自动修好陈旧文件后才测试。每条命令单独记录完整输出及退出码；出现失败先保留现场。环境缺失记 BLOCKED，不能跳过后总报绿。

仓库根目录先按顺序运行：

```bash
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
cargo clippy --locked --all-targets --target x86_64-pc-windows-msvc -- -D warnings
```

前端目录 `ui/`：

```bash
npm ci
npm run verify
npm run test
npm run build
npm run verify
```

前端重建或任何修复后，重新跑根目录上述四条。构建若改动产物/fixture，审查 diff，不能直接 reset 掩盖不一致。必要的源码和产物必须同步；不要求跨平台构建字节完全一致，溯源戳与产物不变量是硬门槛。

Windows 原生额外运行（交叉 clippy 不能替代它）：

```text
cargo test --locked --target x86_64-pc-windows-msvc
cargo clippy --locked --all-targets --target x86_64-pc-windows-msvc -- -D warnings
cargo build --release --locked --target x86_64-pc-windows-msvc
target\x86_64-pc-windows-msvc\release\cpe_test.exe --help
```

发布包按 `.github/workflows/build.yml` 的完整逻辑核验条目及字节，并校验 SHA-256。改动 dist 配置/文档时，读实际 Cargo 版本后运行 `python3 dist/build_config_docs_bundle.py <版本号>` 与 `shasum -a 256 dist/cpe_test-v<版本号>-windows-config-docs.zip`，比较同名 `.sha256`。校验现有包要先执行再重建，避免掩盖陈旧包。最终加 `git diff --check`。

## 6. 组合覆盖、压力预算和长稳步骤

完整协议核心矩阵为：ping v4/v6 × ab/ba/bidir；iperf TCP/UDP × v4/v6 × ab/ba/bidir；CTS TCP/UDP × 当前实际支持的 IP 版本 × ab/ba/bidir。先在一组 Windows 健康有线链路全部执行，再对 Wi-Fi↔Wi-Fi 的合计模式和有线↔Wi-Fi 全部重复适用项。CTS 不支持项测启动前门禁。将 Windows 10/11 和剩余实际网口角色用成对组合分配到矩阵，列出覆盖表，不宣称做了所有笛卡尔积。

必须显式保留高风险交叉：Wi-Fi bidir + 丢一腿；UDP 32+32 + stop；2 流小腿 + 失败重试；CTS UDP + AB/BA 角色；大 socket buffer + 输出延迟；Verify 无目标 + 项目重跑；计划预览后 Wi-Fi PHY 抖动；主控丢 start 响应 + 服务端已执行。数值边界优先用可重复合成数据，真机不强求制造精确的 1000.000 Mbps。

长稳建议作为本次稳定版验收预算，须在开跑前记录测试机对应的最终预算，不可看到失败后放宽：

1. 健康 Windows 双机预热 10 分钟，采集空闲和灌包 CPU、工作集、句柄、线程、子进程、监听端口、HTTP 延迟基线。
2. 连续 24 小时轮换 ping/iperf TCP/UDP/CTS TCP/UDP，覆盖单向、双向、高并发；短轮转保证覆盖，至少一项较长有效窗口验证持续采样。另跑 100 次启动/停止；单轮接近上限的时长通过 fake clock 测租约边界，真机上限场景若省略需明确风险。
3. 资源每分钟采样；每轮记录 run_id、完成数、预期数和错误分类。记录滚动窗口的工作集、句柄、线程趋势，不能只截最后一张图。
4. 建议性能预算：控制 API 正常负载 p95≤2 秒且不触发客户端超时；监控/进度更新不超过当前轮询间隔加实际请求耗时；打开控制台前后健康吞吐三轮中位数下降≤5%。未控背景和 Wi-Fi 干扰时结果标待复核，不能直接归因 UI。
5. 建议资源预算：预热后同负载条件的每小时工作集、句柄、线程不持续单调增长；收尾清理后工作集相对起始空闲增长≤max(50 MiB, 10%)、句柄/线程恢复到测定正常波动带，无本次 owner 残留灌包进程。若缓存有设计上限，记录上限与实际平台占用并验证最终平台期。
6. stop、异常退出、租约分别有不同回收路径。执行前从当前源码提取其超时与 sweep 周期，填入子用例的最大回收时限；到期逐项核对两端资源。不能统一猜一个 30 秒时限，也不能无限等到“最终消失”就通过。
7. 任一崩溃、死锁、持续资源泄漏、数据丢失、错误 PASS、重复起流立即登记阻断；留 dump/日志/采样和 owner 信息，清理后才能继续下一项。

## 7. 执行记录与缺陷闭环

每个子用例至少保存：父 ID/子 ID、日期/执行者、提交 SHA、exe SHA-256、两端 OS/驱动/工具版本、拓扑与原始配置、操作步骤、预期、实际、状态、run_id、证据路径、缺陷 ID、清理结果。网络/命令日志中的真实 token 脱敏，配置语义保持可复现。

建议证据目录：`<工作区外证据根>/<候选SHA>/<子用例ID>/<时间>/`。保存 stdout/stderr、原始 RX/TX 样本、窗口时钟事件、rows.jsonl、meta.json、request.json（适用时）、报告 ZIP、HTML/XLSX、浏览器控制台/网络日志、资源曲线；不把大体积或含身份数据的实测归档直接提交仓库。

缺陷记录包括最小复现、期望/实际、影响层级、原始证据、责任模块、修复 SHA、回归范围及复测结论。间歇失败必须追踪原因，不能靠重跑成功抹掉第一次失败。产品契约不确定时标 BLOCKED 并给出最小例子供用户裁定。

补测试遵循：先复现红灯，再修复，再绿灯；不可降低门限、放松断言、删用例、改默认预设换通过。判定/配置/协议/身份修改需执行其全部联检模块，并重新跑完整检查；仅展示修复也需前端构建与产物、文档同步，不能漏 Rust 产物检查。

## 8. 合入门槛与最终报告

合入前必须同时满足：

- 所有 P0 子项 PASS；必测范围没有 BLOCKED/NOT_RUN，Windows 双机、CTS 和默认 Windows 预设有真实证据。
- P1 全部执行；仅不适用项可有经过说明的 NA；任何影响使用的未修缺陷须显式列出并由用户决定是否接受，Claude 不自行宣布豁免。
- 全套质量检查、原生 Windows 测试/release、前端产物和分发包校验通过；无新增非预期兼容性变化。
- 正常健康链路的判定与独立复算一致，失败注入得到预期结果；长稳、100 次启停、崩溃恢复及多出口对账完成。
- 证据绑定最终修复 SHA 与真正测试的 exe。测试后有新代码或目标分支变化，重新分析影响并验证候选合并结果；不得拿之前分支的报告直接证明新合并树。

最终报告必须列出计划/已执行/PASS/FAIL/BLOCKED/NA 数量（父项和子项分别统计）、环境矩阵完成度、自动化命令退出码、缺陷清单、长稳曲线、未测范围及具体原因，并给出“建议合入”或“暂不建议合入”。本任务不授权自动提交、推送、合入或发 tag；完成后由用户处理合入决策。
